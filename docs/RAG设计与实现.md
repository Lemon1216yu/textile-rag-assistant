# 织知 RAG：设计与实现

本文对应 `enterprise/` 工作台的当前代码，说明实现方式和取舍。项目是个人实践，业务资料为模拟数据；文中的历史验证不表示本次重新测试。

## 1. 需求如何转化为实现

从纺织资料查询出发，我把问题拆成三个部分：先保证资料能正确入库，再保证检索范围与结果可靠，最后让使用者能够核对答案。规格书里的面料编号、单位、适用条件和版本，往往与答案正文同样重要。因此项目没有只做一个聊天接口，还补充了资料审核、检索过程展示和来源核对。

| 场景 | 设计选择 | 可检查的证据 |
| --- | --- | --- |
| 编号精确，但描述口语化 | BM25 与向量分别召回后融合 | 查看改写问题与阶段数量 |
| 同一段落被多个切片覆盖 | MMR 选择后去重 | 对比候选与最终引用 |
| 规格书更新，旧答案仍在历史中 | 发布状态与阅读权限再次校验 | 替换版本后检查新问答和旧会话 |
| 连续追问省略面料编号 | 提取明确条件，补全下一次检索 | C240 后追问“它的缩水率呢” |
| 用户要求批准出货 | 路由到人工工单 | 查看工单记录，不生成放行承诺 |

## 2. 建库：保留可追溯的信息

入口为 `enterprise/ingestion.py`。PDF 按物理页提取文本，保留章节信息；默认切片上限 400 字符、重叠 56 字符，不跨 PDF 页。标题、章节和正文参与向量编码，文档版本、部门与面料编号作为过滤条件。

这个切分方式便于页码溯源，也便于在界面检查和调整。代价是跨页内容可能断开，按长度切分也不能保证复杂表格完整。当前没有自动 OCR 和通用表格还原能力；扫描文件需要先转换，重要数字必须核对原文。

资料上传后由后台任务处理，索引完成后仍需审核发布。维护人员可以检查片段、修改切片设置并重建索引。这样的状态区分避免把未经检查的资料直接用于回答。新旧版本的可见性由发布状态约束，不依赖模型判断哪个版本更新。

## 3. 检索：每一步承担不同职责

实现入口为 `enterprise/rag.py` 的检索逻辑，以及 `enterprise/lexical.py`、`enterprise/local_models.py`。

1. **确定范围。** 先从数据库取得当前用户可以读取的已发布文档，结合面料编号约束候选；不是先检索全库、最后只在页面隐藏结果。
2. **双路召回。** BM25 处理词项与编号，向量召回处理语义相近表达。本地向量存储在 SQLite，按授权范围做余弦计算；配置 Milvus 时走其适配查询，并复核返回资料。
3. **RRF 融合。** 使用排名而非直接相加两个不同尺度的分数，参数为 k=60。
4. **MMR 与去重。** 相关性权重 0.7，最多选取 16 个候选，再消除同文档中的重复文本，减少上下文被重复内容占满。
5. **精排与证据选择。** 本地 BGE Reranker 对问题与候选打分，最多保留 6 个引用片段，正文总长度最多 7000 字符。本地证据阈值默认 0.08，是开发配置；云端模型不能直接复用该分数。

这些参数是当前实现的起点，不是经过大规模实验得到的最优值。是否需要每一步，应该通过同一题集上的对照和失败案例判断。

## 4. 回答、会话与权限

系统根据问题走知识查询、澄清、人工处理、业务边界或问候路由。配置模型时可使用结构化路由输出；同时保留规则与字段校验。实时库存等问题会提示尚未连接业务系统，审批类问题创建人工工单。

会话记录包含近期轮次、明确提取的事实条件和较早问题摘要。近期窗口最多 15 轮，另有长度预算；面料条件按用户和会话隔离，可清除和过期。启用生成模型时可以压缩较早用户问题；未启用或调用失败时使用截断记录。这里没有把所有历史消息无上限地拼进提示词。

无证据时说明不足；没有生成模型时返回原文摘录，向量检索和精排仍可以运行。配置生成模型后，使用检索证据与允许读取的上下文构造回答。引用能帮助核对来源，但有引用本身不保证结论正确，仍需另行评估答案与证据是否一致。

返回前再次检查账号、权限和来源状态。历史回答也通过 `visible_turn` 复核来源，文档权限或发布状态变化时隐藏相关内容。此设计是为了处理“回答生成之后权限改变”的情况。

## 5. 如何定位一次错误

| 现象 | 优先检查 |
| --- | --- |
| 问不到已上传的资料 | 索引是否成功、是否发布、账号部门、面料编号是否一致 |
| 引用页有内容但缺了单位 | 原文解析与切片预览，是否跨页或表格拆散 |
| 候选中没有目标段落 | 改写条件是否错误、词项与向量召回是否覆盖 |
| 候选中有目标但最终没有 | MMR、精排、证据阈值是否过滤过度 |
| 检索正确但回答结论不对 | 生成模式、提示词与引用一致性，不能只调整召回 |
| 追问串到另一款面料 | 事实条件、清除记忆、新会话边界 |

“依据与过程”显示的是实际链路记录。精排分数用于排序，不是回答正确概率。

## 6. 验证现状和下一步

[存档结果](retrieval-evaluation.json) 包含 9 道可回答题、1 道无答案题：BM25 与混合链路 Hit@6 均为 1.0，MRR@6 分别为 0.926、0.944。变化来自一题的目标排名从 3 到 2。数据不足以支持业务准确率或效率提升的结论；当前脚本不评估生成回答和查询改写。

推荐演示时走完整闭环：上传 LY317 → 查看切片 → 未发布时查询 → 审核发布 → 再问并核对数值与版本。然后补充部门权限、连续追问和人工工单演示。详见[手动验收清单](../手动验收/验证步骤.md)。

后续优先顺序：扩充业务标注集与难例，评估无答案拒答和引用一致性；按失败原因调整切片或检索；最后再根据企业系统接口与授权方案接入企微、ERP 或 SSO。尚未实现的集成不计入当前成果。
