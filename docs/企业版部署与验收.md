# 织知企业工作空间 · 部署与验收手册

本工程是根据已确认需求新实现的企业内部知识助手，不是对过去公司项目代码的还原。历史项目模型版本、线上规模和效果指标仍待本人核实。模拟资料不能作为真实生产工艺、质量或商业承诺的依据。

## 1. 使用形式与边界

本次选择独立 Web 工作台。员工用浏览器登录，管理员统一更新服务；回答旁边可以直接核对资料版本、出处和人工处理结果。对于跟单、营销、研发的桌面工作，这种形式便于同时阅读长文档和多轮对话。以后可添加飞书入口、SSO 或移动端，但当前没有接入这些系统。

界面采用中性色、固定工作侧栏、中央对话区和资料详情弹窗，包含浅色/深色及窄屏布局。不是 Codex 的产品复制，也不使用其品牌标识。

## 2. 工程分层与真实技术栈

```text
员工浏览器（React + TypeScript + Vite / Radix / Markdown）
    ↓ 同源 HTTPS、服务端会话、CSRF
Nginx → FastAPI → LangChain LCEL 问答链路
                  ├─ 意图路由 → 澄清 / 知识问答 / 人工工单 / 数据边界
                  ├─ BM25 + Milvus 向量召回 → RRF → MMR → 百炼 Rerank
                  ├─ Qwen 生成 → 引用编号校验 → 再次权限校验
                  ├─ MySQL：账号、会话、版本、片段、任务、工单、审计
                  └─ Redis：限流、跨进程会话锁、关键事实缓存
独立索引 worker ← MySQL 持久化任务表 ← 文档上传
```

MySQL 是事实源，Milvus 保存可重建的向量索引，原文件保存在独立 Docker 卷。当前 worker 使用数据库任务表与比较更新领取租约，没有假称使用 Celery 或 arq。单企业部门隔离，不是多租户 SaaS。

开发模式可使用 SQLite、进程内锁和词面检索，界面明确显示“原文检索”。生产模式缺少 MySQL、Redis、Milvus、生成模型、Embedding、Rerank 或 HTTPS 配置时拒绝启动，不静默降级。

## 3. 从零到一的落地顺序

1. **确定问题范围。** 跟单先做打样登记与交期确认流程；营销做面料参数与推荐规范；研发做工艺资料检索。库存、订单进度和经营数据需要 ERP 等实时来源，当前只说明边界。放行、投料、赔偿及业务承诺转人工工单。
2. **指定资料责任人。** 共享制度由管理员维护，部门资料由相应知识维护员上传。每份资料填写版本、部门、面料编号；上线前由业务人员确认正文、适用范围、失效条件。
3. **建立文档发布流程。** 文件上传进入排队，worker 校验哈希、解析、切片、Embedding、写索引，成功后进入待审核；管理员审核后发布。新版本发布与旧版本下架在 SQL 事务内完成。未审核和下架资料不进入问答。
4. **接通检索与问答。** 先做部门/发布状态过滤，再执行词面与向量召回。向量检索传入当前有效文档集合，结果仍经 SQL 校验。融合、去重、重排后，最多六个片段进入生成上下文；回答带资料版本和片段引用。
5. **建立多轮上下文。** 最近最多 15 轮作为窗口，但仍受字符预算裁剪；移出窗口的用户需求形成摘要；明确的面料、成分、组织、克重写入关键事实。事实包含来源问题和更新时间，Redis 按用户与会话隔离，默认 24 小时有效。SQL 持久化是恢复依据。
6. **验证异常。** 检索为空不编造；生成服务异常可重试；越权文档返回 404；账号停用会使已有登录失效；资料下架后历史答案重新检查引用权限。清空记忆保留历史记录，但创建新的上下文边界。
7. **小范围试点。** 先由三个部门各自的资料责任人试用，收集答非所问、引用错误、版本冲突、需要人工确认的案例。真实效果以固定业务评测集测量，不用模拟资料的命中率代替线上指标。
8. **再决定放量。** 对真实并发、长文档、模型预算、故障恢复做容量测试，然后确定部署资源与开放人数。本工程没有预先承诺并发量、95% 准确率或 35% Token 节省。

## 4. 本机检查

管理员现在可以通过“工作空间管理 → 模型与服务”填写模型、地址与 API Key，测试连接后保存，新请求无需重启即可生效。详见 [模型配置设置](模型配置设置.md)。生产初次部署仍需先满足基础设施、HTTPS 与必需模型配置校验；界面设置支持后续管理和轮换。页面保存值优先于同用途的环境变量。

在项目目录 PowerShell 执行 `./start-enterprise.ps1`，打开 http://127.0.0.1:8766 。本地初始账号保存在 `tmp/enterprise-access.txt`，请勿提交或公开。脚本是开发启动入口，生产使用下一节 Docker 流程。

原来的轻量版 保留在 `app/` 与 `static/`，端口 8765，启动入口 `start.ps1`。企业版在 `enterprise/` 与 `frontend/`，使用独立数据库和鉴权。两者不共享登录或数据库。

可依次检查：

- 新对话问“C240 的成分、克重和用途是什么”，打开引用与处理过程，再追问“它的缩水要求呢”。
- 问“这批次可以直接放行吗”，进入人工工单查看管理员处理结果。
- 在知识库上传模拟 TXT/MD/DOCX/文字 PDF，等待“待审核”，核对内容后发布并检索。
- 使用营销成员账号访问研发文档，应不可见；未经发布的资料应不被成员检索。
- 下架已引用资料，再打开旧会话，答案应隐藏敏感内容并提示重新提问。
- 打开会话记忆，检查事实来源和窗口；清空记忆后继续独立问题。

## 5. Linux 内网部署

先准备 Docker Engine 与 Compose，规划内网域名、可信 TLS 证书、持久化磁盘、备份位置和百炼区域。镜像版本需要经过企业漏洞扫描与审批；示例固定版本仅提供可重复验证的基线，不代表已通过安全审计或高可用验收。

以下在仓库根目录执行：

```bash
python scripts/prepare_deploy.py --origin https://knowledge.company.internal:8443
chmod 700 deploy/secrets
```

生成器不会覆盖已有配置。当前本机已有样例域名配置，真正部署时应为目标环境重新生成独立密钥。修改 `deploy/secrets/app.env`：

- `PUBLIC_ORIGIN` 必须与员工访问的协议、域名和端口一致，`COOKIE_SECURE=true`。
- 填写 `LLM_API_KEY`、`EMBEDDING_API_KEY`、`RERANK_API_KEY` 和真实 `RERANK_URL`；区域、模型授权、Embedding 维度应一致。不要把密钥放入前端或发到聊天中。
- 当前默认生成模型为 `qwen3.5-flash`；Embedding 默认 `text-embedding-v3`、1024 维；Rerank 默认 `gte-rerank-v2`。实际账号不支持时调整配置，并重新评测。更换 Embedding 后创建新集合、重建文档索引，不能混用维度或模型。
- 百炼原生重排接口使用 `RERANK_FORMAT=dashscope`；OpenAI 风格的兼容重排接口使用 `compatible`。以所选区域官方接口为准。
- `BOOTSTRAP_EMAIL` 改成真实管理员账号。首次创建后从应用运行配置移除 `BOOTSTRAP_PASSWORD`，通过账户页面修改初始口令。
- 模板使用 Milvus root 完成初始化。正式开放前为应用配置集合所需最小权限的服务用户，替换 `MILVUS_TOKEN`；不要将 root token 交给员工或前端。

将证书和私钥分别放到 `deploy/secrets/tls/fullchain.pem` 和 `privkey.pem`。`compose.env` 默认只监听 127.0.0.1；内网开放时把 `BIND_ADDRESS` 改为目标内网网卡地址，并由网络侧限定允许的办公网段。基础数据库端口不对外开放。

```bash
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml config --quiet
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml build
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml up -d mysql redis etcd minio milvus
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml run --rm migrate
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml run --rm --no-deps api python -m enterprise.cli bootstrap-admin
docker compose --env-file deploy/secrets/compose.env -f deploy/compose.yml up -d api worker gateway
```

生产不会自动创建模拟账号或导入模拟资料。SQL 迁移由 Alembic 执行，不在 API 请求中改表。生产关闭交互式 Swagger 页面。数据库、Redis、Milvus 和应用没有公网端口。

开发机若要单独联调基础设施，可附加 `-f deploy/compose.local-infra.yml`，只映射本机回环地址 13366、16386、19536。此覆盖文件不得用于生产部署。

## 6. 上线前的验收记录

自动测试命令：

```bash
python -m pytest -q
cd frontend && npm ci && npm run build
```

当前阶段验证结果见 [企业版验收记录](企业版验收记录.md)。单元测试使用的假模型响应只验证接口合同和错误处理；不能据此宣称已验证百炼真实回答质量。

业务验收至少包含同编号不同版本、跨部门问题、扫描 PDF、供应商矛盾参数、上下文更正、恶意文档指令、越权访问、账号停用、模型超时、Redis/Milvus 不可用与进程重启。每个案例保留问题、预期来源、实际来源、回答、延迟与错误原因。准入阈值由业务和运维共同确认。

## 7. 运行维护与恢复

- `/health/live` 只表示进程可响应；`/health/ready` 检查数据库、Redis、Milvus，外部模型是否可用需独立合成探测。管理页显示“已配置，待验证”不等于服务已连通。
- 索引任务持久化，租约 15 分钟，Embedding 每批续租。异常任务显示原因，维护员可以重试；三次进程中断达到上限后转失败。
- 审计记录登录、发布、下架、管理动作和问答状态，不记录密钥；对话和原文仍属于企业业务数据，应由企业确定保留期限与访问权限。当前未实现自动归档清理。
- Compose 对应用日志做大小轮转。当前提供健康检查与业务审计，没有宣称已接入 Prometheus、SIEM 或外部告警。
- 单机 Compose 是初始部署形态，不保证高可用。正式服务需验证主机故障、磁盘满、网络出口限制、备份恢复和资源告警。

备份脚本会短暂停止 API/worker，保存一致的 SQL 与原文快照，然后恢复进程：

```bash
python scripts/backup_enterprise.py --output /encrypted-backups/zhizhi/2026-09-24
```

目录必须不存在；备份包括对话和账号哈希，应存放在加密且限权的位置。配置密钥和 TLS 证书应由独立密钥管理流程保管，不混入普通业务备份。

恢复应先在**全新隔离环境**演练：校验 manifest 中的 SHA256，启动新的 MySQL/Redis/Milvus，在空数据库中导入 SQL，将原文归档恢复到 `/opt/zhizhi/data/enterprise-files`，把原文所有者设为 UID 10001，然后执行 `python -m enterprise.cli rebuild-vectors`。向量从 SQL 的片段向量恢复，不额外调用 Embedding；模型或维度不一致时明确拒绝。Redis 事实可从 SQL 恢复，不必迁移旧缓存。确认账号、资料数量、引用和权限后再安排切换。脚本不会自动覆盖现有生产数据库。

## 8. 已知限制与下一阶段

目前不包括扫描件 OCR、病毒扫描、DLP/脱敏网关、SSO、飞书、ERP、自动工单分派、跨资料事实一致性判定或语义级引用支持校验。已实现引用编号校验，但一个合法编号不等于每句话都被原文支持，仍需真实业务评测。

结构化条件抽取覆盖显式编号及部分成分/组织/克重，不能宣称任意复杂工艺条件都能正确解析。多面料比较会要求拆分核对。BM25 每次请求构建授权语料，默认最多 5 万切片，适合受控规模试点；更大规模需持久化词面索引与性能优化。

SSE 提供真实处理状态、心跳和最终结果，目前不是逐 Token 流式生成。未接入真实模型时显示原文摘录，不能用界面完成度替代模型质量、容量或生产安全验收。
